# RFC 7049 vs RFC 8949 — what "an RFC 7049 implementation" can mean

## Summary

- RFC 8949 (Dec 2020) **obsoletes** RFC 7049 and does **not** change the wire format: "keeping full compatibility with the interchange format from RFC 7049 … This document does not create a new version of the format." (`sources/rfc/rfc8949.txt:3487-3491`). A conforming RFC 8949 decoder is a conforming RFC 7049 decoder.
- The **only** behavioural divergence is the *optional* canonical/deterministic profile: RFC 7049 §3.9 "Canonical CBOR" sorts map keys **length-first**; RFC 8949 §4.2.1 sorts **bytewise lexicographic**. RFC 8949 keeps the old order as "length-first core deterministic encoding" (§4.2.3, "Old Canonical CBOR").
- The two orders are **identical when every key in a map has the same major type** (all text strings, all uints, or all nints) — verified below. They diverge for mixed-type keys, e.g. COSE-style `1, 3, -1, -2` labels.
- So "not RFC 7049" can only be a real defect if (a) the protocol requires 7049 canonical encoding *and* uses mixed-type keys, or (b) it is shorthand for a missing feature that both RFCs share (indefinite lengths, f16, tags, strict-mode duplicate detection, text-keyed map derive, …). Which reading applies is an **open question for the user**.

## Key-ordering divergence — ran it

`experiments/key-ordering/ordering_divergence.py` (random 6-key maps, 20k trials, seed 7049):

```
text keys only: divergence in 0.0% of random 6-key maps
uint keys only: divergence in 0.0% of random 6-key maps
nint keys only: divergence in 0.0% of random 6-key maps
uint + nint (COSE-style labels): divergence in 85.6% of random 6-key maps
uint + text: divergence in 56.5% of random 6-key maps
```

The script also reproduces the RFC's own example orderings exactly (8949 §4.2.1 and §4.2.3).

Why the single-type case coincides: within one major type, preferred serialization makes the head bytes grow monotonically with argument/length, so bytewise order already puts shorter encodings first. Ties at equal length fall back to a bytewise compare in both schemes.

## Design implication (inference)

For a derive-generated struct-as-map, the key set is known at compile time, so either canonical order can be emitted with **zero runtime sorting cost** by ordering fields during macro expansion. Runtime sorting, which needs buffering and possibly alloc, is only needed for dynamic maps.
